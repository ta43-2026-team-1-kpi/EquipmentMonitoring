# ADR 0002. Тести на справжньому PostgreSQL і контроль двох моделей

**Статус:** прийнято

## Контекст

Застосунок працює на PostgreSQL (`PostgresEquipmentMonitoringDbContext`), а більшість тестів — на SQLite in-memory зі звичайним `EquipmentMonitoringDbContext`. Модель для PostgreSQL описана окремо від конфігурацій у `Configurations/*.cs`. Тож тести не перевіряли:

- модель, яка реально працює в контейнері;
- обробку помилок PostgreSQL у репозиторіях (SQLSTATE `23505`, `23503`, назви обмежень);
- PostgreSQL-міграції;
- відмінності трансляції запитів: `timestamptz`, `date`, `GROUP BY`, пагінацію, фільтровані унікальні індекси.

## Рішення

1. **Testcontainers.** На весь прогін піднімається один контейнер PostgreSQL. Міграції застосовуються один раз до бази-шаблону, кожен тест отримує свою копію через `CREATE DATABASE ... TEMPLATE`. Образ береться з `docker-compose.yaml`, тож тести йдуть на тій самій версії, що й стек.
2. **Що покривають тести на PostgreSQL** (`Category=PostgreSQL`):
   - міграції;
   - обмеження і перетворення помилок бази на прикладні винятки;
   - запити;
   - транзакції та конкурентне підтвердження попередження;
   - HTTP-сценарії через `Program` з продакшн-реєстрацією сервісів, середовищем `Docker` і міграціями на старті;
   - `/health/ready` при недоступній базі.
3. **`ModelParityTests`** порівнюють обидві моделі: таблиці, колонки, ключі, індекси, зовнішні ключі, назви check-обмежень. SQL, специфічний для провайдера, не порівнюється. Розбіжність дає читабельний список відмінностей.

Об'єднати дві моделі в одну конфігурацію поки не беремося: це зміна продакшн-коду без функціональної потреби. Тест вимагає від обох моделей однакового результату, і це закриває головний ризик.

## Наслідки

- SQLite-тести лишаються репрезентативними для продакшну: якщо модель розійдеться, тест про це скаже.
- Для повного прогону потрібен Docker. Без нього: `dotnet test --filter "Category!=PostgreSQL"`.
- Прогін PostgreSQL-тестів займає близько 10 секунд, разом зі стартом контейнера.
