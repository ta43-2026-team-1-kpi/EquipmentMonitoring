# ADR 0001. Продакшн-конфігурація окремими compose-шарами

**Статус:** прийнято

## Контекст

`docker-compose.yaml` закриває вимоги ЛР3: три сервіси, мережа, volume і `.env`. Ним уже користуються, і на нього спираються скрипти `scripts/lab3-*.ps1`. Продакшну потрібне більше: секрети, закрита мережа бази, healthcheck API, ліміти, бекапи. Якщо вносити все це в базовий файл, зміниться поведінка звичного `docker compose up`, і зламаються ручні сценарії.

## Рішення

Відмінності описуємо в окремих файлах, які Compose об'єднує поверх базового:

- `docker-compose.prod.yaml` — продакшн;
- `docker-compose.monitoring.yaml` — Grafana і симулятор, підключається поверх prod;
- `docker-compose.dev.yaml` — порт бази для запуску API з IDE.

Де об'єднання списків дало б неправильний результат, використовуємо `!override`: мережі `db` мають замінитися, а не доповнитися.

## Наслідки

- Базовий запуск і скрипти ЛР3 працюють без змін.
- Різницю між середовищами видно в одному файлі, а не розкидано по копіях.
- Запуск продакшну довший: `-f ... -f ...` або `COMPOSE_FILE`. Це описано в [operations.md](../operations.md).
- Шари залежать від імен сервісів і мереж базового файлу. Якщо їх перейменувати, CI-перевірка стеку (`verify-stack.ps1`) упаде.
